# Multi-Server DHCP: what changed, how to use it, what's next

This server can now run as a **cluster**: several DHCP servers that answer the
same network, share one view of every lease, and keep working when any one of
them dies. With no cluster settings it runs as a single server, like before,
except that leases are now stored in a crash-safe journal.

  day-to-day, failures

## What changed

### For everyone (single server too)

| | Before | Now |
|---|---|---|
| Lease storage | `members.txt`, rewritten on every ACK | **`misc/leases.journal`**: append-only text, one line per lease change, `fsync`ed **before** the client gets its ACK |
| `members.txt` | `device_id,mac,ip,hostname`, the actual database | `device_id,mac,ip,hostname,expires,node`, **derived** from memory, sorted by IP, and includes every static assignment |
| Restart | every lease got a fresh 24 h window | leases come back with their real expiry |
| Power cut | writes weren't `fsync`ed, so a file could come back empty | journal is `fsync`ed; every rewritten file uses temp + `fsync` + rename + `fsync(dir)` |
| Declined addresses | reserved in memory until restart | journaled, held for one lease period, then returned to the pool |
| Compaction | hourly rewrite of `members.txt` | hourly (or `kill -USR2`) rewrite of the journal down to live records |
| Address already in use | offered anyway; only caught if the client itself noticed | **ARP probe before a first offer** (ping for relayed clients); a taken address is logged with who has it, held back, and the next one offered (`probe_timeout_ms`, default 500) |
| `misc/dhcp.conf` | regenerated by `make` whenever the template changed | created once, never overwritten; `make config-diff` shows new options |

**Upgrading is automatic.** The first time the new binary starts and finds no
journal, it imports the old `members.txt`. Nothing to do by hand.

**Bugs fixed along the way:**
- A static device lost its fixed IP after going offline for longer than a
  lease. The ACK path gave the static entry an expiry, and the sweeper then
  freed the address.
- A DHCPRELEASE from a static device freed its static address until restart.
- Only the first 4 KB of `static_list.txt` was read at startup. Reloads read
  the whole file.
- Changing a static's IP in `static_list.txt` never took effect. It now applies
  on SIGHUP: the device is NAKed at its next renew and picks up the new address.
- The README said addresses were assigned randomly. They're sticky: each device
  starts searching the pool from a spot derived from its own ID.

### New: cluster mode

- Any number of DHCP **nodes** (tested with 2 and 3), plus an optional
  **controller**.
- Nodes replicate every journal line to each other over an authenticated TCP
  link (port 647).
- Failover is automatic, with no controller needed.
- A controller holds the shared config (`cluster.conf`, static list,
  blacklist), pushes it to the nodes, and keeps the combined `members.txt`.
- An operator tool: `dhcp_server --ctl <conf> status | partner-down <id> | push`.
- Several nodes (and the controller) can run on one machine, sharing its
  address (`make instance`), mixed with nodes on other machines.

New source files: `src/journal.c` (lease journal), `src/ha.c` (buckets,
slices, failover states), `src/peer.c` (peer link), `src/cluster.c` (shared
config). New dependency: `libssl-dev` (for HMAC-SHA256 and SHA-256).

## How it works

```
              ┌──────────────── controller (optional) ────────────────┐
              │ owns cluster.conf + static list + blacklist, pushes    │
              │ them; receives every journal line; combined members.txt│
              └───────┬──────────────────────────────────────┬────────┘
                      │                                      │
   relay / LAN ───► node A  ◄══════ journal lines ═══════►  node B ◄─── relay / LAN
  (every request    answers the buckets it owns          answers the buckets it owns
   reaches every    hands out new IPs from slice A       hands out new IPs from slice B
   node)
```

**No front server.** Every node gets every request, from the LAN broadcast or
from a router relay (`ip helper-address` pointing at each node). Every node is
a complete DHCP server.

**Buckets decide who answers.** Each client's `device_id` hashes into one of
256 buckets. Each bucket belongs to one node, chosen by rendezvous hashing
over the nodes that are currently up. Only the owner answers a DISCOVER or
broadcast REQUEST. If a node dies, only its buckets move, spread across the
survivors. When it comes back, they move back.

**Slices decide who may hand out which address.** Each pool address belongs to
one node, again by rendezvous hashing, but over the *configured* node list, so
slices don't shift when a node goes down. A node only hands out *new*
addresses from its own slice. Two nodes therefore can't offer the same address,
even when they can't reach each other. Renewing an existing lease works on any
node.

**The journal is the source of truth.** Every lease change is one line:

```
A 48213 1790361335 LEASE 01AABBCCDDEEFF AA:BB:CC:DD:EE:FF 192.168.1.57 1790447735 laptop
^origin ^seq ^time  ^op   ^device_id      ^mac              ^ip          ^expires   ^hostname
```

`(origin, seq)` is unique across the cluster. Nodes send new lines to each
other as they happen. A node that was away asks "send me A's records after
seq N" (the `hw` values in `--ctl status` show how far it has got). If two
records disagree about a device or an address, the newest wins, and every node
reaches the same answer. So a node's `members.txt` shows the **whole cluster**,
not only its own leases.

**Failure handling:**

| What happens | What the cluster does |
|---|---|
| A node stops or crashes | Peers see the TCP connection close and take over its buckets **immediately**. Its clients keep their addresses when they rebind at T2 (87.5% of the lease). |
| A node goes silent (power, network) | Same, after `peer_timeout` (default 10 s) without a heartbeat. |
| Any node is unreachable | Everyone else caps new leases at `mclt` (default 1 h), so any disagreement heals quickly. |
| Network split: nodes can't see each other but both serve clients | Both answer all buckets, but each hands out only its own slice, so **no duplicate addresses**. They merge automatically when the link returns. |
| A node is gone for good and its slice is needed | An operator declares it **partner-down**. After `mclt` seconds the survivors may use its free addresses. |
| A client renews with a lease this node never heard of (its issuer died before replicating) | Accepted if the address is free and in the pool ("adopted"), rather than NAKed off the network. |
| A node restarts | It stays in `STARTING` (answering nothing) until it has caught up from its peers, then goes `NORMAL`. |

**Peer link security.** Every message is signed with HMAC-SHA256 using
`peer_key`. The signature covers both sides' random nonces and a message
counter, so recorded traffic can't be replayed. Nodes only accept members
listed in `cluster.conf`. `--ctl` connections are only accepted from
localhost. The link is **authenticated, not encrypted**: lease data (MACs,
IPs, hostnames) is readable on the wire, just as DHCP itself is.

## Using it

### Single server (what you run today)

Nothing changes except the files:

```bash
sudo make                 # sudo: bin/ and misc/dhcp.conf are root-owned here
sudo kill $(cat misc/server.pid)
sudo cron_scripts/dhcp-startup
cat misc/members.txt      # now with expiry + node columns, sorted by IP
tail -f misc/leases.journal
```

The first start imports your current `members.txt`.

> `make` creates `misc/dhcp.conf` only if it doesn't exist, and never
> overwrites it after that. When the template gains new options, `make` says
> so, and `make config-diff` shows them.

### A two-node cluster (no controller)

On **each** machine (A = 192.168.1.2, B = 192.168.1.3):

1. **Build it:** `sudo apt install libssl-dev && make`.
2. **Create one key and copy that same file to both machines.** On A run
   `make peer-key`, then copy `misc/peer.key` to B (e.g. with `scp`).
3. **Set the shared config.** Copy `misc/cluster.conf.example` to
   `misc/cluster/cluster.conf`, list both nodes, set the pool, and move
   `static_list.txt` and `blacklist.txt` into `misc/cluster/`. **All three files
   must be identical on both nodes.** If they differ, the nodes stop handing
   out new addresses until they match (renewals keep working), so a
   half-finished edit can't cause duplicates.
4. **Enable cluster mode.** In each node's `misc/dhcp.conf`, set its own
   `server_ip` and uncomment the cluster block:
   ```
   node_id      A            # B on the other machine
   cluster_dir  /home/avilo/dhcp/misc/cluster
   peer_key     /home/avilo/dhcp/misc/peer.key
   ```
5. **Start both nodes**, then check:
   ```bash
   sudo bin/dhcp_server --ctl misc/dhcp.conf status
   ```
   ```
   self A role=node state=NORMAL buckets=123/256 config=v0/e544d912a00419f1 mclt=3600s journal=A:57,B:61
   peer B node 192.168.1.3:647 UP heard=0s ago skew=0s config=v0/e544d912a00419f1
   link B out 192.168.1.3 unsent=0B
   ```
   Across all nodes, `buckets` should add up to 256, and `config` should match
   everywhere.

If clients sit behind routers, point each VLAN's DHCP relay at **both**
nodes, e.g. `ip helper-address 192.168.1.2` and `ip helper-address 192.168.1.3`.
Don't forget firewalls: TCP 647 between members.

### With a controller

The controller is the same binary started with `role controller` (or
`--controller`). It doesn't answer DHCP and doesn't bind port 67, so it can
run on its own box or next to a node. If it shares a box with a node, give it
a different `peer_port`, and set that port on its `controller` line in
`cluster.conf`.

- **Controller** `dhcp.conf`: `node_id C`, `role controller`, `cluster_dir`,
  `peer_key`. Its `cluster_dir` holds the **real** `cluster.conf`,
  `static_list.txt` and `blacklist.txt`, with a `controller C <ip>` line in
  `cluster.conf`.
- **Nodes** `dhcp.conf`: `node_id`, `cluster_dir`, `peer_key`, plus
  `controller <controller-ip>`. Their `cluster_dir` can start **empty**. On
  first start they fetch everything from the controller and save a copy, so
  later they can start with the controller down.

To change anything shared (pool, DNS, statics, blacklist, members), edit the
files **on the controller only**, then:

```bash
sudo kill -HUP $(cat misc/server.pid)                # on the controller
# or, with a result printed:
sudo bin/dhcp_server --ctl misc/dhcp.conf push
```

The config version goes up, and every node picks it up within a second.
Check with `--ctl ... status` on any member.

### Several servers on one machine

Run as many nodes as you like on one machine, mixed with nodes on other
machines. They all **share the machine's address**. Each one only needs its
own node id and its own peer port. Nothing sits in front of them:

- **Broadcasts** (most DHCP traffic) reach every server on the machine,
  because the kernel hands each one a copy. Only the one that owns the
  client's bucket answers.
- **Packets sent to the address** (renewals, and anything from a router relay)
  go to exactly one of the servers, picked by the kernel.
  - A renewal is answered right there, since every server has every lease.
  - A relayed request for a client that belongs to a sibling is handed to that
    sibling over the peer link, because new addresses must come from the
    owner's share of the pool. The sibling answers the client directly.
  - Any server can do this handing-off, so no single process is in the path.
- **To clients the machine looks like one DHCP server** with one address.

`make instance` sets one up:

```bash
make instance ID=A2                        # shares this machine's address; next free peer port
make instance ID=A3 PEER_PORT=649
make instance ID=C  ROLE=controller PEER_PORT=6700   # the controller, on this machine too
```

Each one gets `misc/instances/<ID>/dhcp.conf` plus its own journal,
`members.txt`, log and pid file. Then:

1. **Add the member line** to `cluster.conf`, e.g. `node A2 192.168.1.2 648`.
   Do this on the controller, or on every member if you don't have one.
2. **Start it:** `sudo cron_scripts/dhcp-startup`. This starts the main server
   and every instance, and skips any that are already running. It also runs at
   boot, and the nightly maintenance covers every instance too.

Talk to one particular instance through its own config:
`sudo bin/dhcp_server --ctl misc/instances/A2/dhcp.conf status`. `members.txt`
has a `node` column, so you can see which instance issued each lease.

Without a controller, instances share `misc/cluster/` with the main server.
With a controller, each one keeps its own pushed copy. (An instance can have
a separate address instead, e.g. `make instance ID=A2 IP=192.168.1.12`, if you
ever want that. It then just has to be assigned to the machine.)

**What this does and doesn't buy you:**
- **Rolling restarts and upgrades with no gap.** Restart one instance at a time
  and the others cover its clients, including renewals sent to the shared
  address. A crashed process is covered too.
- **It doesn't protect against the machine itself failing.** Power, SD card or
  network problems take down every instance on it together. Keep at least one
  node on a *different* machine.
- **Every node counts equally.** Three nodes on Pi #1 and one on Pi #2 means
  Pi #1 answers about 3/4 of clients and owns about 3/4 of the pool. If Pi #1
  dies, Pi #2 can only hand out *new* addresses from its own quarter, until you
  declare the dead nodes partner-down. Existing clients keep their addresses
  either way. Size the pool, or run as many nodes on each machine as you want
  it to carry.

### Adding and removing nodes

- **Add:** add a `node D <ip>` line on the controller and push. Then start D
  with `node_id D` and a `controller` line. D syncs, takes its share of the
  buckets and slices, and starts answering. Existing leases are untouched.
- **Remove:** delete the line and push. The removed node notices it's no
  longer a member and stops answering. Leases it issued stay valid, and the
  others renew them.
- **Safety check:** the controller **refuses** to push a member-list change
  while any current node is unreachable, because that node might still be
  handing out addresses from its old slice. If it's really gone, use
  `--ctl misc/dhcp.conf push --force`.
- **Without a controller:** update `cluster.conf` on every node, then HUP each
  one. New addresses pause until they all match.

### Day-to-day

| Task | Command |
|---|---|
| Cluster health | `sudo bin/dhcp_server --ctl misc/dhcp.conf status` |
| Who has what (the whole cluster) | `cat misc/members.txt` |
| Watch leases happen | `tail -f misc/leases.journal` |
| Reload shared config | `kill -HUP` (controller: push; node: re-read `cluster_dir`) |
| Dump everything, incl. offers and declines | `kill -USR1`, then read `misc/leases_current.txt` |
| Compact the journal now | `kill -USR2` |
| Declare a dead node partner-down | `sudo bin/dhcp_server --ctl misc/dhcp.conf partner-down B` |

Run `partner-down` on the **controller**, which forwards it to every node, or
on each surviving node. It refuses if the target is up, if it's this node, or
if the clocks disagree by more than 30 s. It clears itself when the node
comes back.

### When a node dies

1. You don't have to do anything. Clients in its buckets move to the survivors
   within a second (crash or stop) or `peer_timeout` (silence). Existing leases
   keep their addresses when they rebind.
2. New leases are capped at `mclt` until everyone is back.
3. Survivors hand out new addresses only from their own slices. If a slice
   fills up (logged as `this node's slice is full`), either bring the node
   back or declare it partner-down. **Size the pool** so that each slice can
   hold all the clients one node might have to serve alone. With two nodes,
   keep normal use under about 50%, or widen the range.
4. When it comes back, it catches up and resumes its buckets automatically.

**Clocks matter.** Records carry real timestamps, so every member should run
NTP. `status` shows the `skew` to each peer, and a warning is logged above
5 s.

## Configuration reference

**Per node: `misc/dhcp.conf`** (all existing keys still work)

| Key | Default | Meaning |
|---|---|---|
| `journal` | next to `lease_db` | the lease journal |
| `node_id` | unset (single server) | this member's id: 1–15 of `A-Z a-z 0-9 _ -`. Setting it turns on cluster mode. |
| `role` | `node` | `node` or `controller` (or the `--controller` flag) |
| `server_ip` | | the machine's address, which is also the DHCP server id. The server also listens on it specifically and replies from it. Several nodes on one machine share it. In cluster mode it must be an address of this machine. |
| `cluster_dir` | next to `lease_db` | holds `cluster.conf`, `static_list.txt`, `blacklist.txt`, `version` |
| `controller` | unset | `<ip> [port]`: where to fetch `cluster_dir` from |
| `peer_key` | next to `lease_db` | shared secret, at least 16 characters, `chmod 600` |
| `peer_port` | 647 | TCP port for the peer link |

In cluster mode the pool (`start_ip`/`end_ip`), `subnet_mask`, `gateway`,
`dns`, `ntp`, `domain` and `lease_time` come from `cluster.conf`. So do the
static list and blacklist, from `cluster_dir`. The local `static` and
`blacklist` keys are ignored.

**Shared: `cluster_dir/cluster.conf`**. See `misc/cluster.conf.example`.

| Key | Default | Meaning |
|---|---|---|
| `node <id> <ip> [port]` | | a DHCP node (at least one) |
| `controller <id> <ip> [port]` | | the controller (optional) |
| pool / network keys | | as in `dhcp.conf` |
| `mclt` | 3600 | lease cap (seconds) while any node is unreachable. **Not final**, see below. |
| `peer_timeout` | 10 | seconds of silence before a peer counts as down |
| `auto_partner_down` | 0 (off) | declare a silent node partner-down on our own after this many seconds |

**Command line**

```
dhcp_server [-v] [--controller] [--node-id ID] [dhcp.conf]
dhcp_server --ctl [dhcp.conf] status | partner-down <node> | push [--force]
```

`-v` also logs to stderr. `--ctl` talks to the server on this machine over the
peer port, so it needs to read `peer_key` (run it with sudo).

## Testing

```bash
make test        # or: python3 tests/run_tests.py bin/dhcp_server [test-name ...]
```

No sudo, and nothing touches your real network. (`make test` does build
`bin/dhcp_server` first. A running server keeps using its old copy until you
restart it.) The tests build a private
virtual LAN inside a user and network namespace: a bridge, three nodes, a
controller and a client that impersonates any number of devices
(`tests/dhcpc.py`). They check, among other things:

| Test | What it proves |
|---|---|
| `single_basic` | DORA, renew, rebind, init-reboot, NAK, statics, decline, release |
| `conflict_check` | a device squatting on an address (and ignoring ping) is caught by ARP; a relayed client's address is checked by ping; the taken address stays held back |
| `single_restart_and_migration` | old `members.txt` import, crash with a half-written journal line, compaction, restart |
| `pair_splits_work` | exactly one answer per client, from the right node and the right slice. Both nodes' `members.txt` are identical. |
| `failover_and_return` | kill a node: rebinding clients keep their IPs, leases are capped at MCLT. Bring it back: it catches up, and leases return to full length. |
| `partition_never_duplicates` | cut the peer link: both nodes serve everyone, no address is handed out twice, and they merge cleanly afterwards |
| `partner_down_takes_slice` | slice exhaustion, operator partner-down, MCLT wait, then the returning node learns what happened |
| `restart_catches_up` | a node that was down syncs every lease it missed |
| `unknown_lease_is_adopted` | a lease whose issuer died before replicating is accepted, not NAKed |
| `relay_goes_to_bucket_owner` | relayed (giaddr) requests follow the same bucket rules |
| `controller_pushes_config` | empty nodes fetch config, a HUP pushes changes, adding a node is refused while one is down, then a third node joins live |
| `peer_link_security` | wrong key rejected, unknown node id rejected |
| `same_host_instances` | three nodes sharing one machine's address plus one on another machine: one answer per client from the right node and slice, renewals to the shared address, relayed DISCOVER and REQUEST handed to the owning sibling, one instance dies and its clients keep their addresses |

The Python test code carries its own copy of the server's hash functions, so
it can check independently which node should own each client and each address.

## What's next

Roughly in order of value:

1. **Decide the MCLT.** It's configurable (`mclt`, default 1 h) and the tests
   use 120 s. Shorter means clients renew more often during an outage; longer
   means disagreements take longer to heal. One hour matches what ISC used.
2. **Try it on real hardware.** Two Pis, then a real router relay. The tests
   cover the logic on virtual links; real switches, relays and SD-card
   `fsync` latency haven't been measured yet.
3. **Multiple subnets.** Choose the pool by `giaddr` so one cluster can serve
   many VLANs through relays. Right now there's one pool per cluster.
4. **Dashboard.** Have `../http_server` show the controller's `members.txt` and
   the `--ctl status` output.
5. **DNS integration.** Have the controller write active leases as a hosts
   file for `../dns/auth_dns`, so every device gets a name under your local
   zone.
6. **Removing statics and blacklist entries at runtime.** Reloads still only
   add and update, as before. Removing an entry needs a restart.
7. **Option 82 (relay agent info)** in the journal: which switch port a device
   is on.
8. **Key rotation** for `peer_key` without restarting every member at once
   (accept two keys during a changeover).

Not planned: SQL, a front server in the packet path, speaking ISC/Kea's
failover protocol, DHCPv6.
